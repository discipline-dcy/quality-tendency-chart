## 〇、数据来源（已确定）

需求方指定口径：

| 角色 | 接口 | 取哪个字段 |
|---|---|---|
| **分子** | 4「检验异常录入列表」`ProductionInspectionList` | 不良数 |
| **分母** | 5「检验日报列表」`InspectionDailyReportList` | 检验数量 |

```
良品率 = (分母检验数量 − 分子不良数) / 分母检验数量
```

两个接口同址同鉴权：`http://192.168.0.249/RibaoOA/api/OAWebApi/<路径>`，
GET，入参 `startDate` / `endDate`（`yyyy-MM-dd`）+ `userCode` / `password`。

**接上真实接口后，本方案初稿的三处设定不成立，已按下表修订。**
这不是改主意，是数据源的事实约束：

| 初稿设定 | 事实 | 现在怎么做 |
|---|---|---|
| 横轴按**小时**，看本班次 | 两个接口都只有「检验日期」字段，入参也只到天，**没有小时** | 横轴改成**按日**，默认近 14 天 |
| 小倍数按**产线** | 两个接口都**没有产线字段**。接口 4 有「检出位置」「责任部门」，接口 5 有「检验员」「产品代码」——但责任部门只在分子侧有，没有对应分母，算不出比率 | 小倍数改成**按产品代码**（两边都有，分子分母能对上），按检验量取前 6 位 |
| 每 3 秒刷新 | 数据本身按日更新，且接口文档写明「大数据量查询应缩小日期范围，避免影响 OA 服务」 | 大屏 60 秒轮询本服务，本服务**5 分钟**才向 OA 取一次数，走缓存 |

第一条正好回答了本文第五节口径问题第 5 条（「不良数据多久录入一次」）：**按日**。
初稿里那句警告——「若质检是汇总后才进系统，每小时的粒度就是假的，画成每小时的
折线是在用插值糊弄人」——正是这里兑现的。

### 这个口径的固有风险：分子分母不同源

**接口 5 自己就带「不良数量」字段。** 也就是说单用接口 5 就能算出一个
分子分母同源、天然自洽的良品率。而现在指定的口径是跨两个接口取数：

- 接口 4 是**异常录入**——只有出现异常时才有记录
- 接口 5 是**日报**——每日例行的全量记录

只要两边的记录集合对不齐，比率就会偏，而且是静默地偏：

| 情况 | 后果 |
|---|---|
| 有不良没走异常录入流程 | 分子偏小，良品率被**高估** |
| 异常录入包含日报未覆盖的检验（两边都有「检验类型」字段，口径可能不同） | 分子偏大，良品率被**低估**，极端情况会出现不良数 > 检验数 |

**处理方式：不改口径，但让偏差可见。**

初稿设计的做法是「用接口 5 自带的不良数量算一份对照，差得多就报警」。
**用真实数据（2026-07-16 ~ 07-29）实测后，这条路走不通：**

| 实测 | 数字 |
|---|---|
| 接口 5 里填了「不良数量」的记录 | 100 条里只有 **20 条** |
| 接口 5「不良数量」合计 | **64 件** |
| 接口 4「不良数」合计（当前分子） | **156 件** |

**日报那个字段基本没人填。** 拿它当基准只会天天误报（实测第一版报出
「5.2 个百分点差异」，其实全是这个原因）。

反过来说，**这恰好证明用异常录入当分子是对的**——需求方指定的口径是对的。

所以体检改成盯一件能精确算出来的事：**分子里有多少不良，落在分母根本
没覆盖的检验环节上**。实测确实存在：

```
组件生产 / 组件检验      → 3 件
流水生产 / 流水生产互检  → 2 件
成品改型 / 改型生产互检  → 1 件
                  合计   6 件（占分母 4625 件的 0.13%）
```

这 6 件有分子没分母，会把良品率算低 0.13 个百分点——量很小，但它是**确切的**，
不是「可能对不上」。`crossCheck` 里给出件数、占比和具体是哪些环节，
看板顶部弹提示条。要不要把这些环节排除掉，是业务决策，代码不擅自改口径。

> 两个接口**都有**「检验类型」和「检出位置」字段（文档的「主要字段」一栏
> 漏写了接口 5 的检出位置，实测是有的）。所以如果决定把口径对齐，
> 按这两个字段过滤两边即可，技术上没有障碍。

### OA 账号：服务级，配一次

接口的鉴权方式是每次请求带 `userCode` + `password`，没有单独的登录接口。

**车间大屏没法登录**——它是无人值守的 kiosk，没键盘也没人操作。
所以用**服务级账号**：运维在电脑上打开 `/setup` 配一次，存在服务器上，
大屏之后一直用它取数。

| 设计点 | 做法 | 为什么 |
|---|---|---|
| 没配账号时 | 服务**照常启动**，`/api/quality` 回 503 + `needSetup`，看板显示示例数据并挂提示条 | 直接退出的话，服务器重启后大屏永远起不来，和「无人值守」冲突 |
| 密码存储 | 明文存 `config.json`（已 gitignore） | 接口本身就把密码放 URL 里传；密钥只能存同一台机器，加密等于没加，只制造安全的错觉 |
| 密码回传 | **绝不回传浏览器**，`/api/config` 只回账号名 | 配置页不需要知道密码 |
| 更换 / 清除账号 | 必须先验证**当前密码** | 否则任何能访问这个端口的人都能把服务账号换掉 |
| 验证方式 | 拿真实接口试拉 7 天数据，不抛错即通过 | 没有专门的登录接口可用 |

> **验证有个已知的盲区**：如果账号错了但 OA 返回的是空数组而不是错误码，
> 这里分辨不出来，会当成「通过，只是那几天没数据」。所以验证结果会**带上拿到多少条记录**，
> 拿到 0 条时提示语明确写出来，让人自己判断是真没数据还是权限不对。

### 字段名（已实测确认）

接口文档只给了字段的**中文名**，没给真实 JSON key。已连真实接口实测：
**两个接口返回的就是中文字段名**，`FIELDS` 表里的候选名全部命中，无需修改。

实测还发现文档的「主要字段」一栏是**不完整**的，真实返回的字段更多：

| 接口 | 文档没写、但实际有的字段 |
|---|---|
| 5 检验日报 | 检出位置、月份、周数、**库存分类**、销售分类、品质分类、出货国家、追踪备注、创建人/时间 |
| 4 异常录入 | **不计为不良数**、不良分类、不良编号、流水编号、机器SN、维修人/备注/完成时间、工程判定、问题分类、涉及物料号、责任人、可控性 |

其中三个字段影响了设计：

- **库存分类**（`BCS-160A` / `HCS-3300` / `点钞机半制品`）是干净的机型名，
  用它做小倍数标签。产品名称是一长串规格描述
  （「BCS-160A-110V(美标 清分美元、欧元…12国 内置打印机…）」），五米外放不下。
  但库存分类会**重名**（多个产品代码同属「点钞机半制品」），重名时补产品代码后 4 位区分
- **不计为不良数**：实测区间内**全为 0**，暂不影响口径。但这个字段的存在说明
  「不良数」里可能包含不计入考核的项——见第五节口径问题第 2 条
- **检出位置**（接口 5 也有）：使分子分母对齐成为可能，见上一节

换环境或接口升级后，仍建议跑一次：

```bash
node server.js --probe
```

它会把两个接口的**真实字段名和第一条完整记录**打出来。

## 一、先说清楚这张图给谁看

不是给品质部做分析用的。品质工程师要的是 SPC 控制图、Cpk、分层抽样，那是另一套工具，
坐在电脑前看。

这块屏幕的读者是**班组长和车间主任，站在五米外，抬头看三秒**。三秒内他要拿到的
只有三件事：

1. 现在的良品率是多少，**够不够目标**
2. 哪一天开始变坏的
3. **是哪个产品**

拿不到第 3 条，前两条就没有用——看见数字掉了却不知道去查什么，看板就退化成了装饰。

> 第 3 条初稿写的是「哪条线」。数据源里没有产线字段，只能落到产品代码上（见第〇节）。
> 如果车间实际是按产线追责，那就需要一张**产品代码 → 产线**的对照表，
> 这是接入后要补的第一件事。

下面所有取舍都是围着这三条做的。

## 三、六个关键决策

每条都附上「不这么做会怎样」——因为这些取舍看起来都可以随便改，改了就出事。

### 1. 纵轴不从 0 起（折线图）

良品率的实际波动区间是 96%–99.5%。从 0 画到 100，这条线是一条**直线**，
一整块屏幕什么都没说。

所以折线图纵轴取 `floor(min(数据最小值, 目标值) - 0.5)` 到 100，本例是 95–100%。

截断纵轴是有代价的——它会放大波动。补偿措施有三条，缺一不可：

- 图上**显式写出「纵轴 95–100%（非零起点）」**
- **目标线是真正的锚点**：读者判断高低靠的是「在虚线上还是下」，不是「离底边多远」
- **不画面积填充**。面积的高度隐含「从 0 累计到这里」的意思，纵轴一截断这个意思就是假的
  （原型第一版画了，看了一眼就删掉——那块蓝色在告诉人一个不存在的量）

> **柱状图纵轴必须从 0 起**，没有例外。柱子的长度**就是**数值，截断等于直接说谎。
> 所以下面那张不良品数柱状图是 0 起点，和上面那张不一样，这不是不统一，是两种图的规矩不同。

### 2. 良品率和不良品数拆成上下两张图，不做双纵轴

最容易想到的做法是一张图：左轴良品率（%），右轴不良品数（件），线和柱叠在一起。

**不要做。** 两个纵轴怎么对齐完全是主观的——把右轴的量程调一调，就能让两条线看起来
"高度相关"或者"毫无关系"。这张图会**凭空造出数据里没有的结论**，是图表里最常见也最
严重的错误。

正确做法：两张独立的图，上下堆叠，**左右内边距设成完全一样**，于是时间轴天然对齐。
读者照样能上下对照着看（13 点良品率的谷底，正对着不良品数的峰值），但每张图只有一个
纵轴，没有任何东西被"凑"到一起。

### 3. 六个产品不画成六条折线，而是六张小图

六条折线叠在一张图上，在五米外就是一团蓝黑色的毛线。而且需要六种颜色，
超出了色盲安全的上限。

改成**小倍数**：一个产品一张迷你折线，各自直接标出当前值和状态。
按检验量取前 6 位——量太小的产品，比率本身就不可信（同第 5 条的道理）。

**关键约束：六张小图必须共用同一个纵轴范围。**
如果每张图各自适配自己的数据范围，C-5006 那条 99.2%–99.5% 的微小波动会被拉成一条
剧烈起伏的曲线，看起来比真正出问题的 B-3310 还惊心动魄。**那是在骗人。**

### 4. 只有一个序列色——这条是被工具否掉后改的

原设计：良品率折线用蓝 `#3987e5`，不良品数柱状用橙 `#d95926`（配色表的第 2 号槽位）。
跑配色校验脚本，直接不通过：

```
[FAIL] Normal-vision  #d95926 ↔ #d03b3b（状态色·超标）  ΔE 6.8  —— 低于 15，正常视力都难分辨
[FAIL] CVD separation #d95926 ↔ #0ca30c（状态色·达标）  ΔE 1.4（绿色盲）—— 基本同色
```

也就是说，橙色柱子和红色"超标"标记、绿色"达标"标记在同一块屏幕上会互相冒充。
车间大屏上"红色"是有含义的，绝不能让一个纯粹表示数量的柱子看起来像在报警。

**改法：整个页面只用一个序列色（蓝）。** 良品率和不良品数分属两张独立的图，各自
只有一个序列，本来就不需要靠颜色区分身份——**是标题在区分它们，不是颜色**。
第二个颜色是凭空发明的，发明出来就闯祸。

改完复验，蓝色与三个状态色两两都在安全距离之外（最差 ΔE 25.7）：

| 配对 | 色盲视角 ΔE | 正常视力 ΔE | 判定 |
|---|---|---|---|
| 蓝 ↔ 达标绿 | 27.9 | 30.7 | 通过 |
| 蓝 ↔ 预警黄 | 32.4 | 37.6 | 通过 |
| 蓝 ↔ 超标红 | 25.7 | 31.9 | 通过 |

> 状态色三档之间（红 ↔ 绿 ΔE 4.1）依旧是分不开的——这是已知的，和主看板同一个问题，
> 靠**形状 + 文字**解决：● 达标 / ◆ 预警 / ■ 超标。颜色永远只是辅助通道。

### 5. 样本量太小的日子要标出来

这条最容易被漏掉，也最容易让看板闹笑话。

某天只检了 150 件，坏了 5 件 → 良品率 96.7%。画在图上就是一个**吓人的深坑**。
但它什么也不说明：小批量下坏一件就是 0.7 个百分点。班组长照着这个坑去查，
查不出任何东西，查两次以后他就再也不看这块屏幕了。

处理方式：

| 项目 | 做法 |
|---|---|
| 判定 | 当日检验数 < `minSample`（默认 200 件，需按实际检验量调整） |
| 数据点 | 画成**空心圈**，不是实心点 |
| 线段 | 与之相连的两段线降到 35% 透明度 |
| 柱子 | 降到 45% 透明度 |
| 日期标签 | 一并淡化 |
| 图上说明 | 「空心点 ＝ 当日检验数不足 200 件，比率仅供参考」 |

这和「当天完全没有检验记录」是两回事：那种日子**直接断开**，点都不画（见第二节）。

### 6. 大屏没有鼠标，所有数值必须静态可读

这是这块屏幕和普通网页仪表盘最根本的区别。一般图表把数值藏在 tooltip 里，
鼠标悬上去才显示。**挂在车间墙上的屏幕没有鼠标**，藏进去的值等于不存在。

因此：

- **直接标注**只标两个点：**末点**（现在多少）和**极值**（最差的那个小时）。
  每个点都标数字，五米外就是一片糊掉的白字，等于没标
- 其余数值由**纵轴刻度**承担
- 每张图都配一份**表格视图**（页面底部，默认折叠），任何一个数都查得到
- tooltip 只在「大屏支持触摸」或「有人用电脑打开同一个页面」时才有意义——
  取决于待确认清单业务第 8 题的答复，**不是这块屏幕的主要读取方式**

## 四、接口设计

前端只认自家后端这一个接口，OA 那两个接口的差异全部挡在后端。

```
大屏 ──60s──▶ GET /api/quality ──5min──▶ OA 接口 4（分子）
              （本服务，端口 3200）  └────▶ OA 接口 5（分母）
```

大屏轮询本服务，本服务走缓存，**5 分钟才碰一次 OA** ——
接口文档明确要求「避免影响 OA 服务」，这层缓存就是为此。

```json
    "rate": 97.9,
    "defect": 86,
    "output": 4185,

    "defectDelta": 12,
    "deltaBase": "前一有数据日",
    "latestDate": "2026-07-29"
  },
  "series": [
    { "t": "07-29", "date": "2026-07-29", "output": 4185, "defect": 86,
      "rate": 97.9, "crossRate": 98.1 }
  ],
  "groups": [
    { "name": "A-1024 · 主控板", "spark": [99.2, 99.0, 98.8] }
  ],
  "crossCheck": { "maxGap": 0.2, "onDate": "2026-07-27", "ok": true, "note": "两种口径基本一致" },
  "counts": { "日报记录": 412, "异常记录": 57 }
}
```

字段说明：

| 字段 | 含义 | 备注 |
|---|---|---|
| `target` | 良品率目标线 | 来源待确认，见下一节 |
| `minSample` | 样本不足阈值（件 / 日） | 按实际检验量设定，宁可设高不设低 |
| `summary.rate` | **最新一个有数据的日子**的良品率 | 不是区间平均——区间累计另给 `periodRate` |
| `summary.rateDelta` | 相对 `deltaBase` 的**百分点**差 | 不是百分比，别混 |
| `series[].rate` | 后端算好直接给；当日无检验记录时为 `null` | 前端不做除法，避免分母口径两边不一致 |
| `series[].crossRate` | 用接口 5 自带不良数量算的**对照值** | 只用于 `crossCheck`，不上图 |
| `groups[].spark` | 与 `series` 同长度、同日期刻度，缺数为 `null` | 长度不一致前端不做对齐，直接按位画 |
| `crossCheck.ok` | `false` 时看板顶部弹提示条 | 分子分母不同源的风险出口，见第〇节 |

`null` 必须原样传，**不能用 0 代替**——0 的意思是「检了但全不良」，
`null` 的意思是「那天没检」，画法完全不同。

状态三档由前端按 `target` 判定，不走接口——阈值逻辑只存在于一处：

| 状态 | 条件 | 标记 |
|---|---|---|
| 达标 | `rate >= target` | ● |
| 预警 | `target - 1.5 <= rate < target` | ◆ |
| 超标 | `rate < target - 1.5` | ■ |

## 五、必须先问清楚的口径问题

**这些不问清楚，图画得再对也是错的。** 接口定了之后，其中三条已有答案：

| # | 问题 | 状态 |
|---|---|---|
| 1 | 良品率的**分母**是投入数还是产出数？ | ✅ **已定**：接口 5 的「检验数量」。注意这是**检验数**不是投入数，若品质部报表用的是投入数，两边对不上是正常的，需说明 |
| 2 | 要看**一次合格率（FPY）**还是**最终合格率**？ | ❓ **仍待确认**。接口 4 同时有「不良数」和「维修措施」字段，说明存在返修流程——那现在算出来的到底是哪一个，取决于不良数是否包含返修后合格的件 |
| 3 | **返工品**怎么计？ | ❓ **仍待确认**，同第 2 条 |
| 4 | 目标值 98.5% 从哪来？各产品是否**不同目标**？ | ❓ **仍待确认**。目前 `config.json` 里是全局一个值。若各产品目标不同，接口要按产品下发 target，小图里的虚线各画各的 |
| 5 | 不良数据**多久录入一次**？ | ✅ **已定：按日**。两个接口都只有「检验日期」，没有小时。图已改成按日，见第〇节 |
| 6 | 是否需要**不良原因**分类？ | ✅ **数据有了**：接口 4 带「不良描述」「原因分析」「责任部门」。要不要做排列图是产品决策，不再是数据可行性问题 |

**第 2 条现在是最高优先级。** 它不影响图怎么画，但直接决定这张图**叫什么名字**——
「一次合格率」和「最终合格率」是两个指标，标错了会误导所有看的人。

另外新增一条，由本次接口接入引出：

| # | 问题 | 为什么要问 |
|---|---|---|
| 7 | 有没有**产品代码 → 产线**的对照表？ | 数据源里没有产线字段。若车间是按产线追责，小倍数现在给的是产品维度，对不上责任人。有对照表就能在后端映射回产线 |

## 六、有意没做的东西

| 没做 | 原因 |
|---|---|
| **不良原因 Pareto 图** | 这是「知道了是三号线之后，接着查为什么」的下一步，价值很高，但取决于口径问题第 6 条——数据源里到底有没有原因字段。有的话建议做，一张横向条形图，Top 5 + 其他，单色 |
| SPC 控制图 / Cpk | 品质部的分析工具，读者、场景、精度要求都不一样，不该挤进车间大屏 |
| 良品率排行榜 | 排名会诱发产线之间对着数字博弈（挑简单的单子做），对质量本身没帮助 |
| 缺陷率热力图（产线 × 小时） | 六条线 × 十二小时的格子，五米外看不清；小倍数已经覆盖了同样的信息 |

## 七、落地方式与工作量

原型 `quality.html` 目前用内置模拟数据，双击就能看。接入真实数据只需两步
（`server.js` 在主看板仓库 [production-dashboard](https://github.com/discipline-dcy/production-dashboard)）：

1. `server.js` 增加 `/api/quality` 路由，参照现有 `readProduction()` 写一个 `readQuality()`
2. `quality.html` 里的 `loadQuality()` 改成 `fetch('/api/quality')`——文件里已注释好

渲染逻辑（`renderTrend` / `renderDefects` / `renderSparks` / `renderTable`）**一行都不用动**。

图表全部是**手写 SVG，零第三方依赖**，与主方案「不引框架、单体部署」的选型一致。
没有引入 ECharts 之类的图表库，理由和不引 React 一样：一个 SVG 折线图的代码量比
接一个图表库的配置项还少，而且不用担心 MAXHUB 上的老浏览器内核跑不动。

工作量估计（**前提是口径问题已答复、数据源已确定**）：

| 项目 | 工作量 |
|---|---|
| 后端 `readQuality()` + 路由 | 0.5–1 天（若与生产进度同一数据源） |
| 前端接入 + 现场字号调整 | 0.5 天 |
| 与主看板的轮播/分页切换 | 0.5 天 |

口径问题若未答复，**不要开工**——分母定义改一次，后端的取数逻辑就要重写一次。
