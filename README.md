# 质量趋势图

车间大屏上的良品率趋势图。生产看板的二期扩展，主看板在
[production-dashboard](https://github.com/discipline-dcy/production-dashboard)。

## 快速开始

只想看版面：**双击 `quality.html`**，没有后端时自动用内置示例数据。

连真实数据：

```bash
node server.js       # 没配账号也能启动
```

配 OA 账号有三种方式，都会存进 `config.json`：

```bash
# ① 命令行（推荐）——不用浏览器，回车后再输密码
node server.js --set-account 10639

# ② 直接编辑 config.json，照 config.example.json 填 userCode / password

# ③ 浏览器打开 http://localhost:3200/setup 登录一次
```

①③ 都会先拿真实接口试拉一次数据做验证，通过了才写文件；②不验证，
填错要等启动后才发现。转接到别的机器时优先用 ①——那台机器上未必有
顺手的浏览器，而配账号是部署的第一步，第一步不该依赖浏览器。

不想让密码落盘的话，用环境变量，优先级高于 `config.json`：

```bash
set OA_USER_CODE=10639
set OA_PASSWORD=xxxxxx
node server.js
```

**只需要配这一次。** 之后车间大屏一直用这个账号取数，不需要登录——
大屏是无人值守的 kiosk，没键盘也没人操作，它自己没法登录。

配好后跑一次 `node server.js --probe`，确认接口返回的真实字段名（见下文）。

## 其他电脑怎么打开

服务绑的是 `0.0.0.0`，同一个内网里的机器都能访问——车间大屏、班组长的
电脑、主任的手机都一样。**启动时控制台会直接打出内网地址**，照着抄就行：

```
  内网访问（大屏和其他电脑用这个）：
    http://192.168.30.153:3200    ← WLAN
  车间大屏（MAXHUB 安卓适配版）：
    http://192.168.30.153:3200/quality-maxhub.html    ← WLAN
```

注意 IP 是**跑服务那台机器**的，不是你自己那台。在别人的电脑上打
`localhost:3200` 指的是他自己的机器，只会打不开。

打不开时按这个顺序查：

1. **两台机器在不在同一个网段**。手机连的是访客 WiFi、电脑插的是有线，
   这两个网段之间通常是隔离的，IP 再对也连不上
2. **Windows 防火墙有没有放行**。第一次 `node server.js` 时系统会弹窗问
   要不要允许网络访问，点了「取消」就再也不弹了。补一条规则：

   ```powershell
   # 管理员 PowerShell
   New-NetFirewallRule -DisplayName "质量趋势图 3200" -Direction Inbound `
     -Protocol TCP -LocalPort 3200 -Action Allow
   ```

3. **服务是不是还活着**。在服务器本机开 <http://localhost:3200> 试一下，
   本机都打不开就不是网络的事

> 端口对内网开放意味着**任何能连上内网的人都能看到这块看板**，也能打开
> `/setup`。看板本身只是良品率，不算敏感；`/setup` 那边的防线是「换账号
> 必须先验证当前密码」（见下文）。如果需要更严，就在防火墙上按源 IP 收
> 窄，而不是改回 `localhost` —— 改回去大屏自己就先黑了。

> 服务在没配账号时**照常启动**，不会退出。直接退出的话服务器重启后大屏
> 就永远起不来了，和「无人值守」的要求冲突。没账号时看板会显示示例数据
> 并挂一条提示，写明去哪配。

零依赖，只用 Node 内置模块，不需要 `npm install`。图表全部是手写 SVG，
没有引入 ECharts 之类的图表库——理由和主项目不引前端框架一样：一个 SVG
折线图的代码量比接一个图表库的配置项还少，而且不用担心 MAXHUB 大屏上的
老浏览器内核跑不动。

## 车间大屏怎么开

大屏用 **`/board`**，不是 `/`：

```
http://192.168.30.153:3200/board     ← 换成启动时打印的那个内网 IP
```

`quality-maxhub.html` 和 `quality.html` **是同一块看板**——同一个
`/api/quality`、同一套口径、同一批设计决策，一个数字都不差。区别只在于它
按 MAXHUB 的安卓浏览器做了适配：

- 排版从 `clamp()` + `vw` 改成整体按比例缩放。`clamp` 要 Chromium 79，
  而 MAXHUB 常见的安卓 8/9 内核是 58/66，整条声明会作废；且 `clamp` 有上限，
  4K 面板上字号封顶后相对屏幕反而偏小
- flex `gap`（Chromium 84）全部换成 margin，`flatMap`、对象展开、
  `append(a,b)`、`async/await` 一并降级——整体基线压到 Chromium 49
- SVG 的 `width`/`height` 由 JS 量出来写死。老 WebView 上 `height:auto`
  会算成 0 或 150px
- 时间和千分位手写。`toLocaleTimeString('zh-CN')` 依赖设备 ICU，
  不同机器可能给 `14:23:07`，也可能给 `下午2:23:07`
- 切后台/息屏后定时器会被安卓节流甚至暂停，时钟和轮询都会停且不自纠——
  监听 `visibilitychange`，回前台立刻补一次
- 关掉下拉刷新和双击缩放（手指一划就重载页面），首次触摸自动进全屏
  （地址栏在偷高度），并尝试 `wakeLock` 阻止息屏

### 下半区是轮播的

`/board` 的下半区默认**每 15 秒翻一页**：

```
第 1 页  四个类型并排           ← 回答「哪条线拖的后腿」
第 2 页  流水生产 放大           ← 放大页额外摊开三个环节的合格率
第 3 页  组件生产 放大
第 4 页  成品改型 放大
第 5 页  清分机   放大
```

页数是跟着 `types` 走的，不是写死的 —— 接口那边多出或少掉一个检验类型，
轮播自己会加减一页。

**上半区不参与轮播。** 全厂良品率、趋势图、不良品数始终在屏上——班组长
抬头三秒要拿到的第一个答案是「现在够不够」，那个不能等轮到某一页才出现。

留着第 1 页那张并排图，是因为看板的头号任务只有把几条线摆在一起才答得出。
逐页放大能看清每条线自己的形状，却看不出谁最低，两者都要。

调节：

```
/board            默认，15 秒一页
/board?loop=20    改成 20 秒一页（允许 5~120 秒，越界的值当没写）
/board?loop=0     关掉轮播，退回三张小图并排的静态版面
```

几个已经处理掉的坑：

- **各页共用同一条纵轴**。轮播时读者是靠记忆跨页比较的，纵轴一页一变
  比较就完全失效——比不共用纵轴的静态小倍数还糟
- **舞台高度是写死的**，两种页面内容高度不同也不会让 `fit()` 重算根字号。
  否则每翻一页整块看板的字都会跳一下，五米外看就是屏幕在抽搐
- **翻页不用倒计时定时器，记的是「上次翻页的时刻」。** 这是踩过的一个真 bug：
  原来是 `setInterval(15秒)`，而重启它的 `startLoop()` 在数据刷新（60 秒）和
  `visibilitychange` 里都会被调到，每调一次就把倒计时清零重数。**进全屏时
  MAXHUB 会连着抛 `resize` / `fullscreenchange` / `visibilitychange`，
  这些事件来得比 15 秒密，倒计时就永远数不完——表现是「全屏之后只转一次
  就不动了」。** 改成记时刻之后，谁调多少次都不影响进度；安卓把定时器挂起
  后醒来，一比对发现早该翻了会立刻补上；心跳被节流成几秒一次也只是稍微晚点
- **`fit()` 在量到视口为 0 时直接返回。** 全屏切换过程中量到过 0，那时候
  根字号会被算成 `0px`，整块看板塌成看不见，还要等下一次 resize 才可能恢复
- **`render()` 里先起轮播再 `fit()`。** 反过来的话，`fit()` 万一抛异常，
  轮播就再也起不来了——一个渲染问题不该顺手把翻页一起弄死
- **离线快照固定导出并排页**（`export-static.js` 加了 `?loop=0`）。
  快照是剥光 JS 的静态页，轮播到哪页就永远定格在哪页

### 表格视图常驻展开，自动上下滚

大屏底部的表格视图**不折叠**，一直摊在那儿。折叠是给有鼠标的人准备的交互，
而车间这块屏没有鼠标也没人操作——藏起来的值等于不存在。

内容比一屏高，所以放进一个定高的盒子里自己滚：

```
顶部停 3 秒 → 匀速滚到底 → 底部停 3 秒 → 跳回顶端 → 再停 3 秒 → 循环
```

速度 **15 px/秒**，单向滚。**跳回顶端之后要再停一次才继续滚**——跳变是瞬间的，
紧接着就动的话，人分不清刚才是回到了顶部还是画面出了问题；停一拍让顶部
这一屏先落定。上下两端各压一道渐隐，明示还有内容。

嫌快嫌慢在网址上直接调，不用重新部署：

```
/board?scroll=10    10 px/秒，更从容（允许 3~60，越界的值当没写）
/board?scroll=25    回到早先那个偏快的手感
```

> 速度按 **px/秒** 定，不按「一趟滚多少秒」定。表格高度随数据变（产品多一行
> 就高一截），定成固定时长的话，数据一多字就飞得快——正好在内容最多、
> 最该看清的时候读不了。定成速度，读起来永远是同一个节奏。

几处值得留意的：

- **定高盒子是为了让看板总高可预测。** 表格以前是 `<details>`，展开后又高又宽，
  当时 `fit()` 里专门开了个「表格展开就不回缩」的例外。现在表格在自己的盒子里
  滚，看板总高恒定，那条例外删掉了——回缩规则重新没有特例，永远保证一屏
- **表格内容没变就不碰 DOM。** 服务端向 OA 取数有 5 分钟缓存，而页面 60 秒
  重画一次，绝大多数时候表格一个字都没变。重设 `innerHTML` 会把滚动位置打回
  顶端，表格每分钟自己跳一次，看起来像在抽风
- **`fit()` 只重算滚动区间，不重置位置。** 否则每次数据刷新都把表格拉回顶部，
  滚动永远走不完一轮，下半截的数永远露不出来
- **「量到内容放得下就停表」曾经是一条永久死路。** 全屏切换过程中盒子会
  短暂量出 0（`scrollHeight` 和 `clientHeight` 都读到 0），于是定时器被停掉，
  而当时唯一能叫醒它的是 `fit()`——全屏之后不一定还有 `fit()`，表格就再也
  不滚了。**表现是「全屏时表格只滚一次」。** 现在每秒的时钟心跳兼任看门狗，
  定时器死了下一秒就接回来，停表因此变成可恢复的
- **进度按真实经过的时间算**，不再假设定时器精确每 40ms 触发一次。
  被系统节流时，旧写法的 3 秒停顿和滚动速度都会失真

> **电脑版 `quality.html` 的表格也默认展开了，但不自动滚。** 那边有鼠标有滚轮，
> 页面自己动只会跟正在读数的人抢控制权。

**两版是并存的**，`/` 上的原版（电脑看的 `quality.html`）不轮播，也一点没动——
坐在电脑前看的页面自己会动才是干扰。先在大屏上跑一段 `/board`，确认没
问题再决定要不要合并成一个。

> 如果 `/board` 打开后卡片挤成一坨没有间距，说明这台 MAXHUB 的内核比
> Chromium 84 还老，把型号或内核版本告知开发，还有几处 margin 兜底可以补。
> 想查内核版本：在大屏浏览器里打开 `chrome://version`。

## 大屏 APK（可选）

MAXHUB 自带的「HTML 查看程序」关掉了 JavaScript，页面渲染不出来；自带浏览器
又有地址栏和标签页，会被人误触。`android/` 下是个 WebView 壳，只做三件事：
全屏、常亮、用开了 JS 的 WebView 显示看板。

**本地不需要装 JDK / Android SDK / Gradle**（一套 2GB）。构建在 GitHub Actions
上做：推送 `android/**` 下的改动会自动触发，或者去 Actions 页面手动
「Run workflow」，跑完在页面底部 Artifacts 下载。

装到大屏：解压得到 `app-release.apk`，U 盘拷过去点击安装。会拦一次，去
「设置 → 安全 → 允许安装未知来源应用」放行文件管理器。

用法上只有一个手势要记：**长按屏幕**弹出服务器地址输入框。换电脑、换网络、
IP 变了都在这里改，**不用重新打包**。连不上时会自动退到 APK 内置的离线快照
（`assets/quality-static.html`，由 `export-static.js` 生成），并每 90 秒重试联网——
看板宁可显示过期数据也不能白屏，白屏在车间会被当成设备坏了。

> 内置快照是**打包那一刻**的数据，不会自己更新。要刷新得重新导出、拷进
> `android/app/src/main/assets/`、推送、重新装。所以它只是兜底，正常路径
> 仍然是连服务器。

## 换台电脑部署

按顺序走，每条都是实际踩过的。

**① 拉代码。** `main` 上就是完整的，不用切分支：

```bash
git clone https://github.com/discipline-dcy/quality-tendency-chart.git
cd quality-tendency-chart
```

**② 装 Node。** 当前用 v24.18.0。项目里那个 `.msi` 被 `.gitignore` 排除了，
克隆拿不到，自己去 nodejs.org 装。

**③ 配 OA 账号。** `config.json` 不进版本库，新机器上一定是空的：

```powershell
node server.js --set-account <OA账号>
```

**④ 接对网络。** 最关键的一条，接错网后面全白做。这台机器必须和车间大屏
在互通的网段上。已知结论：`RBzongjingban`(192.168.10.x) 大屏能连通；
`ribao_sale_5g`(192.168.30.x) 连不通，3200 和 80 都超时。

**⑤ 放行防火墙。** 第一次 `node server.js` 时 Windows 会弹窗，必须允许，
而且要勾**当前网络类型**对应的那个。这里的 WLAN 被识别为 `Public`，放行规则
也必须覆盖 Public，否则本机自测正常、大屏就是连不上。查现有规则：

```powershell
Get-NetFirewallApplicationFilter | Where-Object { $_.Program -like "*node*" } |
  ForEach-Object { $_ | Get-NetFirewallRule } | Select-Object DisplayName,Direction,Action,Profile
```

**⑥ 验证能取到 OA 数据。**

```powershell
node server.js --probe
```

注意原开发机是**通过代理软件**访问 `192.168.0.249` 的（实测源地址是 TUN 网卡
`198.18.0.1`，`ping` 不通但 TCP 通）。新机器如果没装代理，要确认能否直连 OA。

**⑦ 大屏改地址。** 长按屏幕，填 `node server.js` 启动时打印的那行内网地址。

**⑧ 让服务常驻。** 关掉终端服务就停，大屏立刻掉成离线快照。跑一次这个就行：

```powershell
.\install-autostart.ps1        # 注册开机自启并立即启动
.\install-autostart.ps1 -Off   # 取消自启并停掉服务
```

注册的是**当前用户的登录触发任务**，不需要管理员权限，无控制台窗口，
崩溃后 1 分钟自动重试（最多 3 次）。装完会把大屏该填的完整网址打印出来。

> 用任务计划而不是往 `shell:startup` 放快捷方式，有两个实际原因：快捷方式
> 会在桌面留一个黑框控制台，谁顺手关掉服务就没了；而且快捷方式没有
> 「崩了自动重启」，看板是无人值守的，这条比省事重要。
>
> 代价是**必须有人登录进桌面**服务才会起来。做成免登录的系统服务要存密码，
> 不划算——车间那台机器本来就常年登录着。

> **IP 会变。** DHCP 续租、换网、笔记本漫游到另一个 WiFi 都会换地址，
> 而大屏那头是记死的。排查「大屏突然连不上」时，**第一件事是确认服务器
> 当前 IP 还是不是原来那个**——这个坑踩过不止一次。想彻底免维护，
> 找 IT 做 DHCP 保留，或者申请一个内网 DNS 名（APK 的地址框填域名一样用，
> 以后换机器只改 DNS 一条记录）。

## 数据来源

| 角色 | 接口 | 取哪个字段 |
|---|---|---|
| 分子 | 4「检验异常录入列表」`ProductionInspectionList` | 不良数 −「不计为不良数」 |
| 分母 | 5「检验日报列表」`InspectionDailyReportList` | 检验数量 |
| 组件专用 | 66「组件抽检巡检单列表」`GetComponentInspectionList` | 检验数 / 合格数 |

```
一次合格率 = (检验数量 − 不良数) / 检验数量              改型、硬币清分机
一次直通率 = 电检合格率 × 装配检合格率 × 流水检合格率      流水
一次合格率 = 合格数 / 检验数                            组件
```

**四张卡不是同一个指标。** 口径对齐的是品质部《考核指标》表（见下节
「目标线：季度 KPI」），每张卡上都写着自己是哪个指标，因为它们互相不可比 ——
流水的 82% 和改型的 98% 不是「流水差了 16 个点」，是两把不同的尺子。

**指标名都带「一次」。** 考核表里四项的原名就是「一次合格率」「一次直通率」，
即 first-pass：只认第一次检验判出的不良，返修后合格不回冲。少这两个字会被
读成最终合格率，那是另一个数。

**「不计为不良数」是个文档里没有的字段。** 质量周月报告工具的 README 写的是
「问题分类包含『不计入不良』的异常不计入不良数」，但 2026-08-07 实测近 90 天
939 条异常，问题分类只有 6 个取值（物料 / 设计 / 装配 / 工艺 / 误判漏检 / 空），
**一条「不计入不良」都没有** —— 那条规则在真实数据上是死代码。真正在起作用的
是接口 4 的数值字段 `不计为不良数`：近 90 天 40 条非零、合计 151 件，全落在
流水生产上（+0.60pt）。两条规则本项目都实现了，数值字段为主。

> ⚠ **但报告工具 V1.2 没扣那 151 件**，而考核表「流水一次直通率」的公式栏写的是
> 「同质量周报数据」—— 也就是说考核认周报的数，两边差约 0.60pt。
> 见下文「还没确认的口径」第 5 条，需要品质部拍板。

**接口 4 / 5 都只有「检验日期」，没有小时**，所以趋势图是**按日**的（默认近 14 天），
不是按班次按小时。两个接口**都没有产线字段**，但**都有「检验类型」**——
实测取值是 `流水生产` / `成品改型` / `清分机` / `组件生产`，这就是车间实际的分线方式，
所以小倍数按**检验类型**分组。产品代码维度退到表格视图。
详见 [docs/设计方案.md 第〇节](./docs/设计方案.md)。

组件是个例外：它**根本不填检验日报**（这就是早先「组件生产为什么没有检验日报」
那条待确认项的答案），分母在接口 66 的组件抽检巡检单上，按「抽检巡检时间」归集。
那张单子上还混着流水巡检、成品首检，所以只统计**检验方式含「组件」**的记录 ——
实测近 14 天 499 条里，组件抽检 242 / 组件首检 88 / 组件全检 5 / 组件巡检 1 计入，
流水巡检 127 / 成品首检 36 不计入。

### 各生产类型的实测量级（2026-08-07，近 3 个月）

| 检验类型 | 指标 | 检验数 | 实测 | Q3 目标 | 看板上怎么呈现 |
|---|---|---:|---:|---:|---|
| 流水生产 | 直通率 | 22110 | **84.92%** | 90 | 折线小图，**不达标 5.08pt** |
| 组件生产 | 合格率 | 13733 | 99.88% | 99.7 | 折线小图，达标（保留两位小数） |
| 成品改型 | 良品率 | 7666 | 97.30% | 96 | 折线小图，达标 |
| 清分机 | 良品率 | 626 | 88.82% | 92 | **不画折线**，只给区间值，不达标 |

几条是数据本身的约束，不是偷懒：

- **清分机日均只有 7 件**，远低于 `minSample`。实测它的 7 日滚动率在
  −57% ~ 100% 之间乱跳（有过「当天检 2 件、坏 2 件 → 0%」的点）。
  几个噪声点连成的线，五米外会被当成趋势读，那是无中生有。所以它只给
  区间累计值 + 一句说明，逐日值放表格视图里——**点是实测到的事实，
  线是我们编出来的**，编不出来就别编。
- **流水的日直通率会断点。** 三环节任一环节当天没有检验量就算不出当天的
  直通率，实测近 90 天 62/90 天能算 —— 缺的绝大多数是周日（那天不生产，
  不是漏数据），真正「有生产但环节不全」的只有 3 天。断点处不连线。
  **不套用报告工具 V1.2 那条「检验量和不良数均为 0 时按 100.00% 计算」**：
  那条只用在机型直通率的表格里，日粒度下套它，某环节当天没排产就会被当成
  100% 合格，直通率被系统性抬高，比留空糟得多。
- **流水的小样本要按环节判，不能按当日总量判。** 实测 7-30 那天流水共
  186 件、但电检只做了 15 件，直通率被拉到 43.78%。按总量判它是达标样本，
  按环节判才看得出那个点不可信。近 90 天 24/62 天属于这种，画成空心点。

### 目标线：季度 KPI

**目标线是分类型、分季度设的**，不是一条线管到底 —— 不同工序的基准本来就
不一样，而且目标逐季递增：

```js
流水生产（一次直通率）  Q1 87   Q2 88   Q3 90   Q4 92
成品改型（一次合格率）  Q1 94   Q2 95   Q3 96   Q4 98
硬币清分机（一次合格率）Q1 86   Q2 89   Q3 92   Q4 95
组件生产（一次合格率）  Q1 99.5 Q2 99.6 Q3 99.7 Q4 99.7
```

**出处：品质部《考核指标》表**，质量类共 4 项、权重合计 40%。考核表的
「考核目标值」列给的是 Q1 那一档（87% / 94% / 85%※ / 99.5%），分季度的值
在备注列；另有一列「挑战值」（92% / 98% / 95% / 100%），本项目未采用。
**质量周月报告工具 V1.2** 的 `QUARTER_TARGETS_BY_RANGE`（该项目
`src/main.jsx:44`）用的是同一组数 —— 它和本项目都是下游使用者，考核表才是
源头。14 天窗口跨季度时目标线走阶梯。

> ※ 清分机的「考核目标值」列写 85%，备注里的 Q1 是 86%。本项目按备注列的
> 分季度值走（86/89/92/95），因为看板是按日画的，需要的是每个季度那一档。

**四项在考核表里全叫「一次合格率」「一次直通率」** —— 即 first-pass：分子只认
第一次检验判出的不良，返修后合格不回冲。所以看板上的指标名都带「一次」两个字，
这不是啰嗦，是和最终合格率的区别。

> ⚠ **`config.json` 里全厂合计的 `target: 96.5` 没有对应的 KPI** —— 考核表的
> 质量类只有上面四项，没有「全厂合计」这一档。它仍是「近 3 个月 7 日滚动
> 良品率的 P75」推算出来的。**屏上它画成「参考」线而不是「目标」线，
> 顶部大数字也不再做达标判定** —— 拿一条推算线去给一个混合口径的数打红绿灯，
> 红绿灯本身就是假的。

> ⚠ **考核按「当月」，看板按滚动窗口。** 考核表的公式栏写的是
> 「当月合格数量/总数量」，而看板默认 14 天滚动。跨月时两个数不等价，
> 小倍数面板的副标题里已注明，**别把看板上的数直接抄去上报**。

### 目标线按年分档，明年的数要手动填

**考核表是一年一发的**，所以 `targets` 的第一层是年份、第二层才是检验类型：

```json
"targets": {
  "2026": { "流水生产": [87, 88, 90, 92], "成品改型": [94, 95, 96, 98],
            "清分机": [86, 89, 92, 95],   "组件生产": [99.5, 99.6, 99.7, 99.7] },
  "2027": { "流水生产": [.., .., .., ..], ... }
}
```

程序里**只内置 2026 那一档，2027 及以后不给默认值** —— 给了就等于替品质部
编一个 KPI。跨到没配的年份时，行为是**响的，不是静的**：

| | 表现 |
|---|---|
| 卡片 | 显示「目标未设」，不画目标虚线，状态行写「N 件 · 本年目标未设，不判达标」 |
| 表格 | 目标列「未设」，状态列「—」 |
| 顶部 | 亮黄色告警条，写明是哪一年、去哪儿补 |
| 服务启动 | 控制台打印提醒；每年 10 月起会提前催下一年的考核表 |

这是有意做的。早先 `quarterOf()` 只看月份不看年份，**2027-01-01 那天看板会
不声不响地拿 2026 的 Q1 目标接着画**，一条过期的线挂在车间墙上，没有任何
迹象说明它过期了。宁可没有线，也不要一条假的线。

**只写新增的年份就行**，2026 那档自动保留；同一年里只写要改的类型也行，
其余走内置值（两层都做了合并，不会互相冲掉）。每个类型也接受一个标量，
表示四个季度同一个数。

`targets` 第二层的键必须是 OA「检验类型」字段的原值（`清分机`），改了就
查不到表；屏上显示的名字走 `server.js` 的 `TYPE_LABELS`（`清分机` →
`硬币清分机`，和考核表对齐）。

顺带：清分机那个 85 / 86 的出入（见上文脚注）如果品质部说以 85 为准，
改 `config.json` 里 `targets.2026.清分机` 就行，不用动代码。

大屏 60 秒轮询本服务，本服务 5 分钟才向 OA 取一次数——接口文档明确要求
「避免影响 OA 服务」，这层缓存就是为此。

## OA 账号怎么存的

明文存在服务器的 `config.json` 里，该文件已在 `.gitignore`。

**不做加密。** 这个接口本身就是把密码放在 URL query string 里传的，
而且加密的密钥还得放在同一台机器上——加了等于没加，只会给人一种安全的错觉。
真正的防线是这台服务器的登录权限，请确认只有运维能登上去。

两点保护是有的：

- 密码**绝不回传浏览器**。`/api/config` 只回账号名和配置状态
- 账号配好之后，**更换或清除都必须先验证当前密码**，
  否则任何能访问这个端口的人都能把服务账号换掉

建议单独申请一个**只读的服务账号**，不要用个人账号——个人账号改密码之后
看板就断了，而且 OA 日志里分不清是谁在取数。

## 设计要点

完整说明见 [docs/设计方案.md](./docs/设计方案.md)，这里只列最容易被改错的几条。

**折线图纵轴不从 0 起，柱状图必须从 0 起**
良品率实际只在 96%–99.5% 之间波动，从 0 画就是一条直线。所以折线图截断纵轴，
代价是必须写明非零起点、用目标线当锚点、并且**不画面积填充**（面积隐含
「从 0 累计到这里」，纵轴一截断这个意思就是假的）。柱状图则没有例外——
柱子的长度**就是**数值，截断等于说谎。两张图规矩不同，不是不统一。

**良品率和不良品数拆成两张图，不做双纵轴**
两个纵轴怎么对齐完全是主观的，把右轴量程调一调就能让两条线看起来
「高度相关」或者「毫无关系」。改成上下两张独立的图、左右内边距设成一样，
时间轴天然对齐，但每张图只有一个纵轴。

**各生产类型画成并排小图，且共用同一纵轴**
各图自适配范围的话，某条线 99.2%–99.5% 的微小波动会被拉成剧烈起伏，
看着比真出问题的那条还惊心动魄。那是在骗人。

但共用纵轴有个前提：**参与定标的点得可信**。清分机有过「当天检 2 件、
坏 2 件 → 0%」的点，让它参与定标会把另两条线压成一条平线。所以定标只用
样本量达标的点；个别落到轴外的小样本点夹回画布内并画成空心，具体数值
去表格视图读。

**整页只有一个序列色**
原本给不良品数配了橙色，跑配色校验直接不通过：橙 ↔ 状态红 ΔE 6.8
（正常视力都难分辨）、橙 ↔ 状态绿 ΔE 1.4（绿色盲下基本同色）。
橙柱子会冒充红色报警。两张图各自只有一个序列，本来就是标题在区分它们，
不是颜色——第二个颜色是凭空发明的，发明出来就闯祸。

**样本量太小的时间点要标出来**
12 点午休只做了 115 件、坏 4 件 → 96.5%，画出来是个吓人的深坑，
但它什么也不说明。低于阈值的小时画空心点、淡化线段，并在图上写明原因。

**所有数值静态可读**
挂在车间墙上的屏幕没有鼠标，藏进 tooltip 的值等于不存在。
直接标注只标末点和极值两个（每点都标，五米外是一片糊掉的白字），
其余交给纵轴刻度，再配一份表格视图兜底。

**状态不只靠颜色区分**
● 达标 / ◆ 预警 / ■ 超标，形状加文字。红绿色盲人群约占男性 8%，
标准红与标准绿在其视角下差异值仅 4.1，属于不可辨识。颜色只是辅助通道。

## 首次接入：先跑 --probe

接口文档只给了字段的**中文名**（「主要字段：…检验数量、不良数量…」），
没给真实 JSON key。所以 `server.js` 里的 `FIELDS` 表对每个字段准备了一组
候选名按序尝试。在厂内网跑一次：

```bash
node server.js --probe
```

它会把三个接口返回的真实字段名和第一条完整记录打出来（接口 66 还会额外打出
「检验方式」的分布，这个决定哪些记录计入组件合格率）。对不上就把正确的名字
补进 `FIELDS` —— 只改这一处，其它代码不用动。

## 还没确认的口径

设计方案第五节列了七条，接口定了之后三条已有答案。拿到品质部《考核指标》表
之后（2026-08-08）又结掉两条。

> ~~**看的是一次合格率（FPY）还是最终合格率？**~~ **已解决。** 考核表里四项
> 的原名就是「一次合格率」「一次直通率」，即 **first-pass**：只认第一次检验
> 判出的不良，返修后合格不回冲。看板的指标名已全部改带「一次」。
>
> 遗留的小口子：接口 4 有「维修措施」字段，说明返修确实存在，但**没验证过
> 返修合格的件会不会回头改写原记录的不良数**。真要较真，probe 一次
> 「同一台机器 SN 在接口 4 里出现多次」的情况就能看出来。

改成按「检验类型」分组之后多出的三条，2026-08-07 结掉了两条：

> ~~**1. 三条目标线定多少？**~~ **已解决。** 目标线取自品质部《考核指标》表
> 的季度 KPI（见上文「目标线：季度 KPI」），质量类 4 项、权重 40%。
> 质量周月报告工具 V1.2 用的是同一组数，两边都是下游使用者。
> 全厂合计那条 `target: 96.5` 考核表里确实没有对应档位，已在屏上降级成
> 「参考线」并去掉达标判定。

> **2. 硬币清分机 88.8% 的一次合格率是真的吗？** 它比流水线低了一大截，
> 但样本很小（近 3 个月 626 件），且分子分母对齐得最差：分母侧写「清分机点币」，
> 分子侧却有 20 件写成「点币」、2 件写成「点币检」、2 件写成「装配检」。
> 这 24 件（约占它全部不良的四分之一）**算进了分子，却没有对应的分母**，
> 把它的一次合格率压低了。**先统一录入写法，这个数才有意义。**
> 现在它对着 Q3 目标 92 显示不达标，而这 24 件正是差距的一大半。

> ~~**3.「组件生产」为什么没有检验日报？**~~ **已解决。** 组件不走检验日报，
> 它有自己的单子（接口 66 组件抽检巡检单，近 90 天 2871 条）。分母一直都在，
> 只是不在接口 5 里。现在组件有卡片了，近 90 天合格率 99.88%。

新增两条：

> **4. 流水一次直通率 84.92% 对着 90 的目标，差 5.08pt —— 这个差距是真的吗？**
> 三环节里**电检是瓶颈**：合格率 91.74%，最低；而且它的检验量只有 4720，
> 不到装配检（8669）和流水检（8721）的一半。**同一批机器不是每台都过电检，
> 还是电检的日报漏填了？** 如果是后者，电检的分母被低估，合格率被算低，
> 直通率跟着被压低 —— 那 5.08pt 的差距就有水分。这条直接决定大屏上流水
> 是不是该常年挂红。
>
> 注意这条**不只是本项目的偏差**：考核表里流水那行的公式栏写的是
> 「同质量周报数据」，周报大概率吃的是同一批检验日报，电检漏填的话两边一起低。

> **5. 「不计为不良数」那 151 件，到底扣不扣？** 考核表「流水一次直通率」的
> 公式栏写的是**「同质量周报数据」**，即以周报的数为准。但报告工具 V1.2 的
> `isExcludedDefect` 只查问题分类（真实数据里恒为 false），**没有扣**接口 4 的
> 数值字段「不计为不良数」—— 近 90 天 40 条非零、合计 151 件，全落在流水生产上。
> 本项目扣了（见 `server.js` 的 `netDefect()`），结果是**大屏的流水比周报高约
> 0.60pt，而考核认的是周报那个数**。
>
> 两条路，都得品质部拍板：
> ① 认可本项目的修正 → 同步改 V1.2，两边一致；
> ② 大屏跟周报走 → 去掉 `netDefect()` 的规则 ②，明知多算 151 件也照算。
>
> 在拍板之前保留现状（扣着），因为多算不良数比少算保守。这条只影响流水一张卡 ——
> 另外三项的公式是「当月合格数量/总数量」，不涉及不良数的扣减规则，
> 而那 151 件恰好全在流水上。

另外，**每个类型都有「当天日报一条没有、异常却记了不良」的日子**——
近 3 个月流水 6 天 54 件、改型 5 天 12 件、清分机 5 天 32 件。这些不良
没有分母可配，不计入任何比率，看板顶部会报出件数。属于录入及时性问题，
