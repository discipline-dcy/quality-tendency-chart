# 质量趋势图

车间大屏上的良品率趋势图。生产看板的二期扩展，主看板在
[production-dashboard](https://github.com/discipline-dcy/production-dashboard)。

## 快速开始

只想看版面：**双击 `quality.html`**，没有后端时自动用内置示例数据。

连真实数据：

```bash
cp config.example.json config.json   # 填 OA 账号密码
node server.js --probe               # 先在厂内网跑一次，打印接口真实字段名
node server.js                       # 浏览器打开 http://localhost:3200
```

零依赖，只用 Node 内置模块，不需要 `npm install`。图表全部是手写 SVG，
没有引入 ECharts 之类的图表库——理由和主项目不引前端框架一样：一个 SVG
折线图的代码量比接一个图表库的配置项还少，而且不用担心 MAXHUB 大屏上的
老浏览器内核跑不动。

## 数据来源

| 角色 | 接口 | 取哪个字段 |
|---|---|---|
| 分子 | 4「检验异常录入列表」`ProductionInspectionList` | 不良数 |
| 分母 | 5「检验日报列表」`InspectionDailyReportList` | 检验数量 |

```
良品率 = (检验数量 − 不良数) / 检验数量
```

**两个接口都只有「检验日期」，没有小时**，所以趋势图是**按日**的（默认近 14 天），
不是按班次按小时。**也都没有产线字段**，所以小倍数按**产品代码**分组。
详见 [docs/设计方案.md 第〇节](./docs/设计方案.md)。

大屏 60 秒轮询本服务，本服务 5 分钟才向 OA 取一次数——接口文档明确要求
「避免影响 OA 服务」，这层缓存就是为此。

## 这张图给谁看

不是给品质部做分析用的。品质工程师要的是 SPC 控制图、Cpk、分层抽样，
那是另一套工具，坐在电脑前看。

这块屏幕的读者是**班组长和车间主任，站在五米外，抬头看三秒**。
三秒内他要拿到的只有三件事：

| 问题 | 图上怎么回答 |
|---|---|
| 现在良品率够不够 | 对着目标虚线看，在线上还是线下，不需要读数字 |
| 今天几点开始变坏 | 按小时的折线，谷底直接标数 |
| **哪条线拖的后腿** | 六张迷你图并排，谁掉下来一眼看得出 |

拿不到第三条，前两条就没有用——看见数字掉了却不知道去找谁，
看板就退化成了装饰。

## 设计要点

完整说明见 [docs/设计方案.md](./docs/设计方案.md)，这里只列最容易被改错的几条。

**折线图纵轴不从 0 起，柱状图必须从 0 起**
良品率实际只在 96%–99.5% 之间波动，从 0 画就是一条直线。所以折线图截断纵轴，
代价是必须写明非零起点、用目标线当锚点、并且**不画面积填充**（面积隐含
「从 0 累计到这里」，纵轴一截断这个意思就是假的）。柱状图则没有例外——
柱子的长度**就是**数值，截断等于说谎。两张图规矩不同，不是不统一。

**良品率和不良品数拆成两张图，不做双纵轴**
两个纵轴怎么对齐完全是主观的，把右轴量程调一调就能让两条线看起来
「高度相关」或者「毫无关系」。改成上下两张独立的图、左右内边距设成一样，
时间轴天然对齐，但每张图只有一个纵轴。

**六条产线画成六张小图，且共用同一纵轴**
各图自适配范围的话，五号线 99.2%–99.5% 的微小波动会被拉成剧烈起伏，
看着比真出问题的三号线还惊心动魄。那是在骗人。

**整页只有一个序列色**
原本给不良品数配了橙色，跑配色校验直接不通过：橙 ↔ 状态红 ΔE 6.8
（正常视力都难分辨）、橙 ↔ 状态绿 ΔE 1.4（绿色盲下基本同色）。
橙柱子会冒充红色报警。两张图各自只有一个序列，本来就是标题在区分它们，
不是颜色——第二个颜色是凭空发明的，发明出来就闯祸。

**样本量太小的时间点要标出来**
12 点午休只做了 115 件、坏 4 件 → 96.5%，画出来是个吓人的深坑，
但它什么也不说明。低于阈值的小时画空心点、淡化线段，并在图上写明原因。

**所有数值静态可读**
挂在车间墙上的屏幕没有鼠标，藏进 tooltip 的值等于不存在。
直接标注只标末点和极值两个（每点都标，五米外是一片糊掉的白字），
其余交给纵轴刻度，再配一份表格视图兜底。

**状态不只靠颜色区分**
● 达标 / ◆ 预警 / ■ 超标，形状加文字。红绿色盲人群约占男性 8%，
标准红与标准绿在其视角下差异值仅 4.1，属于不可辨识。颜色只是辅助通道。

## 首次接入：先跑 --probe

接口文档只给了字段的**中文名**（「主要字段：…检验数量、不良数量…」），
没给真实 JSON key。所以 `server.js` 里的 `FIELDS` 表对每个字段准备了一组
候选名按序尝试。在厂内网跑一次：

```bash
node server.js --probe
```

它会把两个接口返回的真实字段名和第一条完整记录打出来。对不上就把正确的名字
补进 `FIELDS` —— 只改这一处，其它代码不用动。

## 还没确认的口径

设计方案第五节列了七条，接口定了之后三条已有答案。**剩下最要紧的是这条**：

> **看的是一次合格率（FPY）还是最终合格率？**
>
> 接口 4 同时有「不良数」和「维修措施」字段，说明存在返修流程。
> 那现在算出来的到底是哪一个，取决于不良数是否包含返修后合格的件。
> 这不影响图怎么画，但直接决定这张图**叫什么名字**——两个指标标错了，
> 会误导所有看的人。

另有一条由接口接入引出：数据源里**没有产线字段**，所以小倍数给的是产品维度。
若车间是按产线追责，需要一张**产品代码 → 产线**的对照表，在后端映射回去。

最后，本项目是否要做，取决于主看板待确认清单业务第 6 题（车间是否需要显示
良品率）的答复——目前仍是候选项。
